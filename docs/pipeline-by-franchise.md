# Pokémon vs One Piece — the same pipeline, and why one of them is hard

Two spreadsheets sit beside this file and carry the per-step detail:

- `docs/pipeline-pokemon.xlsx`
- `docs/pipeline-one-piece.xlsx`

Both are generated by `npm run docs:pipelines`, so they are reproducible rather
than hand-maintained. This file is the narrative for the parts that are hardest
to hold in your head.

Last verified against the codebase on **2026-09-06**.

---

## The shape today

Both franchises now run the same two-tier architecture, and that is new. It used
to be the main difference between them.

```
TIER 1   offline catalogue        identity, on disk, zero API calls
TIER 2   live upstreams           prices and market, metered, only for tracked cards
```

| | Pokémon | One Piece |
|---|---|---|
| Catalogue source | TCGdex (free, unmetered) | BerryWallet (100 calls/hour) |
| Crawled into | `data/catalog/pokemon/` | `data/catalog/one-piece/` |
| Size | 203 sets, 21,066 cards | 109 sets, 10,689 rows, 2,632 codes |
| Price snapshot | `data/prices/pokemon.json`, 20,452 rows | `data/prices/one-piece.json`, 10,505 rows |
| Marketplace pointers | 20,092 Cardmarket (95.4%), 19,679 TCGplayer | Cardmarket + TCGplayer URLs per row |
| Cards tracked live | 3 | 9 |

The catalogue is what makes `/sets` and `/cards` free to render: identity comes
off disk, prices come from a snapshot regenerated at deploy (`npm run prebuild`),
and neither path can spend a metered call. Only a tracked card's product page
reaches a live upstream.

**The tier-1 rule**: `lib/catalog.ts` and `lib/one-piece-catalog.ts` import
`node:fs` and `node:path` and nothing else. They *cannot* reach an API by
mistake, and they hold no prices.

## The one structural difference that remains

**A Pokémon card is a key. A One Piece card is a question.**

`name + set + number` identifies exactly one physical Pokémon card, and TCGdex
answers it for free. By the time anything asks about a price, we already know
which object the page is about.

A One Piece **code is an identity, not a printing**. Measured across the 2,632
codes in our corpus:

| | codes | share |
|---|---|---|
| more than one row | 2,495 | **94.8%** |
| more than one treatment | 346 | 13.1% |
| more than one product | 219 | 8.3% |

`OP05-119` alone spans plain / Alternate Art / Manga / SP / SP Gold / Reprint /
Wanted Poster across five sets, EUR 4.49 to EUR 7,500. So a One Piece lookup
starts under-determined and every layer below exists to close that gap without
guessing.

| | Pokémon | One Piece |
|---|---|---|
| Identity key | name + set + number — unique | card code — ambiguous by design |
| Price history | apitcg | apitcg (BerryWallet has none) |
| EU / Cardmarket | PokéWallet, stored id | corpus row, or a sibling joined on the **TCGplayer product URL** |
| JA identity | PokéWallet, stored id, 1 call | aligning a `(V.N)` index across languages — and **refused** when it can't be |
| JA card number | genuinely different (190/182 → 070/063) | one universal code across regions |
| FR | TCGdex `/v2/fr` | none — BerryWallet has zero French sets |
| eBay searches | 4 conditions × 2 languages = **8** | same 8 |
| eBay query | card **name + number** | **treatment + code**, name discarded |
| Per-card human work | one JP id, sometimes | which printing the code means |

## The One Piece eBay query

This is where most of the work went, and it has its own document:
`docs/ebay-market-pipeline.md`. The summary is that a query is derived from four
independent axes, each one a fact about the card rather than a per-card rule:

| axis | answers | example |
|---|---|---|
| **treatment** | which version | `(manga)`, `(alt,alternate,alternative,altart,parallel)` |
| **product** | which printing of that version | `(prb,"premium booster","the best")`, `-"2nd anniversary"` |
| **rarity** | whether it is this card at all | `-uc -r -sec -l -tr -don` |
| **spelling** | what sellers actually type | `altart`, `alternative`, `parallel` |

```
OP05-119 PSA 10 (alt,alternate,alternative,altart,parallel) (prb,"premium booster","the best")
         -manga -wanted -sp -gold -"2nd anniversary" -awakening -emperors -divine -uc -r -sr -l -tr -don
```

Every term there is derived from the corpus plus two small vocabulary tables
(`src/data/one-piece-sets.ts`). Adding a card requires **no query work**; adding
a new *set* or *product* requires one line, and `npm run prebuild` fails the
build if one is missing rather than shipping a card whose query cannot separate
its own printings.

### Four domain rules that no catalogue could tell us

These came from the card owner and are recorded because they are not derivable:

1. **Parallel and Alternate Art are the same treatment** — Bandai's early sets
   say one, later sets say the other. Corroborated: no code in the corpus
   carries both as separate rows.
2. **Manga is a kind of Alternate Art**, so a Manga card searches `(manga)`
   alone; naming both admits the code's separate plain Alt Art printing.
3. **A Manga Rare's reprint keeps the artwork.** Bandai cannot reissue a manga
   panel under a code that already has one. So OG and PRB-01 printings are one
   market — medians $1,475 and $1,600 on OP05-074.
4. **An Alt Art's reprint does not.** A PRB-01 SEC or SR Alt Art is a new
   picture, and sells for about half — $790 against $400 on OP05-119.

Rules 3 and 4 are the same relationship with opposite answers, which is why the
split is per *treatment* and carried by a flag rather than assumed either way.

## The three Luffys

Three special cards, all resolving their English identity through the same
cross-product path, ending in three different states. The difference is never
the resolver — it is what exists upstream at two specific joins.

Since the corpus landed, a cross-product match also reports its **real
containing set** (`opRowById`), so these pages no longer label a PRB-01 card
"Awakening of the New Era".

### `monkey-d-luffy-op09-061` — every market good

- **Identity**: OP09 holds the number but not the tag → `findVariantAcrossProducts`
  finds the "English Version 2nd Anniversary Set" promo. `crossProduct: true`,
  and the page now names *One Piece Promotion Cards* rather than OP09.
- **EU**: that row's `cardmarket` is null, so `findCardmarketSiblings` adopts the
  `Unnumbered-Promos` row — joined on the **shared TCGplayer product URL**, the
  only thing that proves two rows are the same physical card. EUR 485.65.
- **JA identity**: refused (see below). Name and art stay English.
- **JA market**: **still resolves.** `japaneseCardmarketWithoutIdentity` runs on
  the fallback path precisely because *identity and market data are separate
  facts*. The derived URL redirects to root, so `cardmarketProductUrl.japanese`
  pins the real Premium Bandai Asia-region link: corrects the link, keeps the
  figures.

**Net**: US + EU + JA. The only gap is the Japanese *name and art* — a
translation gap, not a data gap.

### `monkey-d-luffy-st21-014` — US only

- **Set**: no stored code. `prefixCandidates` offers both `ST21` and `ST-21`;
  the real code is `ST-21`. **This card is why that function exists.**
- **Identity**: the Campaign Pack is a separate product → cross-product match,
  one of four rows sharing the code across a **200× spread**.
- **EU**: **missing.** No sibling shares its TCGplayer product, and the two
  Cardmarket products BerryWallet knows for this code are *different printings*.
  Pricing either here is the merge this codebase refuses.
- **JA**: **missing twice** — identity refused, and the market walk needs the
  Western product URL as its entry point.

**Known gap**: this card also sits outside the crawled corpus (it exists only in
BerryWallet's flat search index), so its query takes the positive-only fallback
path and gets no sibling exclusions at all.

### `monkey-d-luffy-op01-024` — no JA

- **Identity**: the tag is the full `(OP01-024) (Alternate Art)`, because the
  origin set names this card `(024)` and every reprint set names it `(OP01-024)`.
  Cross-product match in `The-Best`; the page names *Premium Booster -The Best-*.
- **EU**: **works** — the `The-Best/-V2` row carries its own Cardmarket block.
- **JA**: **missing, and upstream.** PRB-01 holds exactly one `OP01-024` row and
  there is no `The-Best-Non-English` row for this code at all.
- **eBay**: this is the card that proved rule 4 above. Its OG Romance Dawn
  printing and its PRB-01 printing are the same *treatment* in two products, so
  only the product separates them — drop `(prb,…)` and 26 English PSA 10
  listings come back instead of 8, the extras all OG Parallels at $135–245.

### What actually separates them

All three fail the Japanese *identity* step for the same reason: a cross-product
English match has `printVariantIndex: null`, and `pickVariantForJapanese`
refuses to align a `(V.N)` that belongs to another product's tiering. `(V.N)` is
a **per-set index, not an identifier**.

| | Western Cardmarket row reachable? | Japanese row reachable from it? |
|---|---|---|
| OP09-061 | yes (sibling on shared TCGplayer product) | yes → EUR 375.59 |
| ST21-014 | **no** | **no** — the walk has no starting point |
| OP01-024 | yes (own row) | **no** — the row does not exist upstream |

A Western Cardmarket product is not just the EU tab. **It is also the entry
point for the JA tab.**

## What this means for the scan / portfolio product

1. **The catalogue precondition is met.** Per-card live lookups do not scale at
   100 calls/hour; both franchises are now crawled into a local store, and the
   crawl is resumable because that quota cannot hold a full pass.

2. **Variant selection is no longer an API problem.** "Which of these four
   ST21-014 rows is your card" is a map lookup against rows already on disk.
   It remains a *human* decision.

3. **Coverage must be a field, not an error.** A stated absence is a first-class
   render state, and the ST21-014 shape — real card, real market, no row
   anywhere we can read — will keep recurring.

4. **"Which market's card do I own" is only answerable where the JP counterpart
   is.** Anything better needs a real cross-language product mapping — image
   hashing plus price tier, the same evidence used by hand today.

5. **Two things can never be automated away.** Which printing a code refers to
   when several are real; and whether a pinned Cardmarket URL is the right
   variant — Cardmarket answers automated requests with a bot challenge, so
   nothing in the code can ever check it.
